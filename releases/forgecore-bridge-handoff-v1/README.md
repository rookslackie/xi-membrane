# ForgeCore → Xi Vessel Bridge: observed compatibility handoff

Prepared 2026-09-13 for Hunter and Michael Hughes. Synthetic public examples only. This packet documents existing behavior and proposes fixtures; it does not open a remote connection or grant access.

Bridge reference: https://github.com/MichaelWave369/xi-vessel-bridge at commit `302991142811fcea55f75468af337fec4434bb2f`. Source fingerprints are in `source-manifest.json`.

## The first compatibility decision

The existing Vessel exchange helper and the new bridge both call their format `xi.exchange.v1`, but they are **different dialects**. Existing Vessel uses `schema`, `source_system`, `destination_system`, `intent`, `operation_mode`, `constraints`, `payload_media_type`, `verification_required`, and `provenance`. The bridge requires `protocol`, `sender`, `recipient`, `session_id`, and a typed message envelope. Neither should be silently treated as the other.

Recommended first crossing: wrap the complete, unchanged serialized legacy exchange as the bridge capsule's base64-encoded content. `bridge-capsule.json` does this. Its `format: vessel.exchange.legacy` is a proposed adapter label, not a renamed historical standard. The old packet, its provenance, and its integrity digest survive intact. Newly assigned bridge/session/request IDs describe the crossing, not retroactive history.

## XiFabric.v1 capsule mechanics

- `δ`: dialect `XiFabric.v1`.
- `⋈`: payload.
- `Ω`: boundary `{kind,media,field,scope}`; scope is `local` or `public`.
- `⟁`: `sha256:` plus SHA-256 of canonical JSON `{ "⋈": payload, "Ω": boundary }`.
- `⧂`: optional provenance; retained without requiring a fixed author schema.
- `∴`: `transit` marker.
- `⊚`: `b2:` plus a 16-byte BLAKE2s digest of the complete capsule excluding `⊚`.

Canonical JSON here means Python `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))` encoded as UTF-8. It is not a claim of RFC 8785 conformance. Agree on numeric/Unicode edge cases before general cross-language canonicalization.

The content address excludes provenance; the closure includes it. Consequently, equal payload+boundary with different provenance shares a content address. Preserve complete serialized capsule bytes for the bridge hash rather than substituting `⟁` for the bridge's content SHA-256.

Legacy exchange integrity instead hashes the complete exchange before adding `integrity`, using the same compact sorted JSON convention. The existing parser checks shape but **does not verify that digest**. The fixture tests independently verify it. Integrity hashes detect change; they do not identify the sender.

## Two read-only candidates

1. **Proposed alias `forgecore.fabric.verify`** → existing `POST /api/xi/v1/fabric/verify`, body `{capsule: ...}`. Verifies supplied inline data, stores nothing. Live synthetic round-trip passed. `proposed-capability.json` translates this into Michael's advertisement schema; that alias is not deployed.
2. **Proposed alias `forgecore.tessera.grammar`** → existing `GET /api/xi/v1/tessera/grammar`. Returns the canonical grammar description. Source inspected; not invoked as part of this handoff.

Michael's `artifact.sha256` is an excellent shared first fixture. `bridge-request.json` and `bridge-expected-result.json` specify its expected result over the exact bytes of `legacy-exchange.json`. **That expected result is a test vector, not a receipt from a deployed bridge or Michael's system.** Its execution count is the expected first execution. Replay should return the original result without a second execution.

## First crossing, without changing either core

Use the bridge's hello/session and capability exchange, offer `bridge-capsule.json`, resolve only that accepted inline capsule, execute `artifact.sha256`, and compare with the expected digest. Preserve the legacy content as data. Do not execute embedded intent or constraints as receiver instructions.

For the adapter, bind an idempotency key to the authenticated peer plus request ID, and fingerprint the full operation, input, capsule digest, recipient and relevant permission context. Same ID with different content should return a conflict. Persist the accepted request/result relationship across restarts. These are proposed implementation requirements, not claims about the current native API.

Historical notes from the original inspected commit (both corrected upstream in the updated commit recorded in source-manifest.json): the Python demo uses `recorded_at: "reference-runtime"` while the receipt schema requires a date-time; its replay fingerprint omits `input` and supplied capsule bytes. Resolve those before treating the demo as a production compatibility proof.
